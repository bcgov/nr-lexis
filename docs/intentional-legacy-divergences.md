# Intentional legacy divergences

Modern LEXIS normally preserves functional parity with legacy. Intentional modernizations, security
controls, and approved retirements use the searchable code marker
`INTENTIONAL_LEGACY_DIVERGENCE(<ID>)` and are recorded here so they are not mistaken for parity
defects.

Parity follows what legacy users could see and do, not everything the legacy code could do.
Anything legacy hid or never showed users stays hidden in modern unless the Enhancements Decisions
Log or Figma approves it. This covers features, controls, and edits that legacy locked by status,
role, or type, as well as messages and warnings that legacy handled without telling the user. For
example, a provincial application submission's required status code is ignored without a warning,
as it was in legacy. A server path that the legacy screens never reached is not a legacy workflow.
Approved exceptions are recorded here.

Only observable differences in supported inputs, user workflow, authorization, persistence, or
integration behaviour belong in the divergence table. Refactors, duplicated service-boundary
enforcement, and early validation of existing legacy or database constraints are parity work.
Stored-procedure replacements are listed separately below as an implementation inventory.

Modern's stricter checks apply to values a user creates or changes. Data that legacy stored and
that a save leaves unchanged is accepted as legacy accepted it, so a record legacy could save stays
saveable in modern. This covers permit invoice states, a Ministerial permit's owner taken from its
first application, legacy accented text, package species and end-use codes, and packages and
scales whose application has moved to another exemption or to none. Where legacy's own handling of
such data was a bug, modern takes the simplest correct path, for example cancelling every active
invoice (`PERMIT_CANCEL_EVERY_ACTIVE_INVOICE`).

Business-record searches default to 10 rows, following the Figma All searches Results note.
Application Review defaults to 100 rows, on the business's recommendation, with the same page-size
options. Explicit page sizes in saved search links remain supported.

## Detail-flow functional boundaries

Visual alignment preserves existing role, lifecycle and transaction contracts:

- Active exemption Approval volume stays editable, as in legacy and Figma 3458-45293; an Active
  Ministerial exemption's approved volume must still be at least the total requested volume.
  Approval dates are established by approval; switching a new draft to Ministerial clears a date
  entered for OIC or Blanket OIC.
- A Ministerial permit's applications are chosen in Permit details edit mode, in one Application
  number(s) table: ticking an application includes it, unticking one excludes it, and Current permit
  pieces and volume follow the ticks until Save. Save applies the whole selection in one
  transaction, before any other permit change, with the same relationship checks as before: an added
  application must belong to the permit's exemption, applications are added only to an Active permit
  and removed only from an Active or Payment pending permit, and the scale volume added, less the
  volume removed, must fit the exemption's Balance remaining. An added application becomes Permitted
  and a removed one keeps its status; an application with no unassigned scale rows stays off the
  permit and Save says so. View mode lists the included applications with their pieces and volume on
  this permit. Legacy added applications from a pop-up and removed each one at once. Ordinary Order
  in Council permits keep Add application and Remove in their Associated applications card.
- A saved permit's owner and agent clients stay read-only. Application Approvers,
  Administrators and Provincial Submitters can remove a Blanket OIC permit's agent, or add one when
  it has none, while the permit is Active or Payment pending. A submitter can do so only while its
  client is the permit's saved owner or agent; a submitter that reaches the permit through a linked
  application cannot. One whose client is the saved agent can remove itself, and then reaches the
  permit only through an application of its client that is linked to it. A Ministerial permit's
  agent follows its first linked application and is changed there. Editable fields are not enabled
  merely because a design depicts an input.
- BOIC Add scale uses a drawer with Cancel and Save, matching the legacy dialog's separate save
  boundary. It captures the selected package and retains validation, record-version and in-flight
  guards. Cancel discards only the unsaved scale draft, asking first when it has values.
- Ministerial scale totals remain application-scale quantities; BOIC completed totals remain
  completed-permit quantities. Labels follow the quantity actually returned by the service.
- Application/exemption document tables use their reviewed drawer flow. Permit uploads retain the
  existing validation/review submission flow; their empty/table presentation uses the shared layout.
